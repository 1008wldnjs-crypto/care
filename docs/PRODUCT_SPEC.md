# 재가요양·방문케어 앱 — 제품 명세 (Cursor용)

이 문서는 구현 기준입니다.
- 여기에 없는 내용은 추측해서 만들지 말고 먼저 질문합니다.
- `TBD`로 표시된 값은 임의로 정하지 않습니다. 설정 상수로 분리하고 `TODO(TBD)` 주석을 남깁니다.
- `(제안)`으로 표시된 항목은 초안이므로 구현 전에 확인합니다.

## 0. 현재 상태

- 이미 있음: 제품 명세·체크리스트·플로우 문서, Expo 앱 2개 뼈대 (`care-consumer`, `care-caregiver`)
- 소비자 앱 구현 완료: 시작 → 가입 → 주소 → 홈 → 세부 → 일정 → 예상 가격 → 신청 → 매칭(지원자 선택/자동/재요청) → 매칭 확정 → **채팅(목)** → **결제(목, 카카오페이 기본)** → **리뷰(목)**. 상주 상담·앱 안 고객센터. 단가는 `catalog.ts` 임시값
- 제공자 앱(`care-caregiver`): 가입 → 프로필 → **의뢰 피드 → 상세·지원 → 내 일정 → 채팅(목) → 도움 완료 → 정산(15% 차감 표시)** 목 UI 구현
- 아직 없음: 소셜 로그인 실연동, PG 실결제, Firebase, 두 앱 실시간 연동
- 이미 동작하는 화면은 요청 없이 수정하지 않습니다.

## 1. 서비스 개요

노인 본인이나 보호자가 집에서 필요한 도움을 앱으로 신청하고, 사회복지사(또는 해당 분야 전문가)와 매칭되어 방문 서비스를 받는 플랫폼입니다.

해결하려는 문제: 가격이 상담 후에야 보임 / 신청 절차 정보 부족 / 누가 오는지 모르는 불안.
해결 방식: 신청 전 예상 가격 공개, 앱 안의 명확한 절차, 매칭 전 프로필·후기와 매칭 후 채팅·리뷰.

앱 이름: **다정**. 코드에는 이름을 하드코딩하지 말고 상수로 둡니다.

## 2. 범위

**1차(Must)**
- 계정, 의뢰 생성·상태 관리, 단가표
- 매칭, 재요청, 조건 조정
- 서비스 완료 후 결제 요청, 15% 수수료 정산
- 취소 규칙, 매칭 후 채팅, 리뷰, 최소 알림
- 상주 카테고리의 1:1 전화상담 신청

**나중(Later, 지금 만들지 않음)**
우리 동네 후기, 알바, 관리자 앱, 단가 원격 수정, 정기구독, 매칭 전 소개 영상, 앱스토어 리뷰 유도, 네이버페이, 정산 고도화

## 2-1. 로그인

신청 전 허들을 최대한 낮추는 것이 목표이므로 1차부터 아래 세 가지를 모두 지원한다.

- 카카오 로그인 (기본값)
- 네이버 로그인
- 전화번호 + 문자(SMS) 인증

카카오를 기본 버튼으로 두고, 네이버·전화번호는 그 아래 다른 방법으로 노출한다. 소셜 로그인 자체를 낯설어할 수 있는 어르신을 위해 전화번호 인증을 대체 경로로 반드시 유지한다.

**1차에서 제외:** Google 로그인, Apple 로그인, 이메일 가입.

## 3. 기술·구조

- React Native (Expo, TypeScript)
- 앱 두 개, 레포도 분리: `care-consumer`(노인·보호자), `care-caregiver`(사회복지사). 모노레포 아님
- 관리자 앱 없음
- 백엔드/DB: **Firebase** (Auth, Firestore, FCM 알림). 정산 계산·취소 수수료 처리 같은 커스텀 로직은 Cloud Functions로 구현
- 지원자 목록 UI(작업 1)는 Firebase 연동 전이므로 서버가 필요한 기능은 인터페이스(타입)와 목 데이터로 먼저 분리해 동작시킨다

## 4. 카테고리와 가격

| 카테고리 | 세부 | 비고 |
|---|---|---|
| 운동 | (기존 catalog 따름) | 건별 신청 |
| 청소 | (기존 catalog 따름) | |
| 케어 | 목욕, 세탁, 외출, 병원동행 | |
| 음식 | 시니어용 식사 배달 | 식사 준비·정리는 추가금 옵션 |
| 공부 | 치매 예방형 인지·학습 | 운동과 비슷한 건별 흐름 |
| 상주 | 체크: 돌봄 시간대(주간/야간/24시간), 식사·투약 관리 필요 여부, 장기요양등급 보유 여부 | 앱 매칭·가격 없음, 전화상담으로 연결. 판단이 필요한 정보(거동·인지 등)는 앱에서 묻지 않고 전화상담에서 상담사가 확인 |

- 알바는 후순위, 1차 제외
- 가격 = 카테고리·세부별 고정 단가 × 시간 (회당 상품은 회당 금액)
- 단가표는 앱 안 설정(`catalog.ts`)에 두고 원격 수정은 없음. 실서비스 단가는 TBD

**상주 흐름:** 선택사항 체크 → 「상담 신청 완료」 → **접수 안내(곧 연락드릴게요)** → 상담사가 전화. 앱에서 즉시 발신은 하지 않음. 구독 결제와 앱 내 자동 매칭은 넣지 않습니다.

## 5. 주요 데이터 (제안)

의뢰 상태 예시:
`REQUESTED`(신청됨) → `OPEN`(지원 받는 중) → `MATCHED`(매칭 확정) → `IN_PROGRESS` → `COMPLETED` → `PAYMENT_REQUESTED` → `PAID` → `SETTLED`
분기: `CANCELLED`, `NO_SHOW`, `NEEDS_ADJUSTMENT`(조건 조정 제안 중)

주요 엔티티: User(소비자/보호자), Caregiver(제공자 프로필), ServiceRequest, Application(지원), Match, ChatMessage, Payment, Review, PaymentMethod

## 6. 소비자 앱 플로우

1. 시작 → 가입 → 주소 → 홈(카테고리)
2. 세부 항목·추가 옵션 → 일정 → 예상 가격 → 신청 요약 → 신청
3. 매칭 대기 → (지원자 목록에서 선택 또는 자동 매칭) → 매칭 확정
4. 채팅 (매칭 이후에만)
5. 서비스 당일 종료 후 결제 요청 → 결제
6. 리뷰
7. 상주: 체크 → 「상담 신청 완료」 → 전화상담

## 7. 제공자 앱 플로우

1. 의뢰 목록(피드) → 상세(할 일, 날짜, 위치, 예상 가격) → 지원
2. 매칭 확정 → 채팅, 일정 수행
3. 도움 완료 처리 → 정산 확인

## 8. 매칭 규칙

- 지원자 1명: 자동 매칭 (목록 없이 매칭 확정 화면)
- 지원자 여러 명: 별점 순 정렬 목록, 소비자가 직접 선택
- 지원자 카드 표시: **이름, 경력, 후기 미리보기, 후기 개수** (사진·별점 숫자는 카드에 표시하지 않음. 정렬에만 별점 사용)
- 경력 표기: 운동 카테고리는 운동 관련 경력(예: "필라테스 강사 경력 3년"), 그 외는 "사회복지사 경력 n년". 가격은 지원자 카드에 표시하지 않음
- 지원자 없음(매칭 대기):
  - 신청 직후 ~ 24시간: 대기 안내만 (재요청 버튼 없음)
  - **24시간 이후**: 재요청 버튼 노출 (수동 1회)
  - **36시간 이후**: 자동 재요청 1회
  - 재요청 후에도 없으면 **앱 안 고객센터 문의 폼**으로 연결 (전화·외부 채팅으로 나가지 않음)
- 방문 24시간 전까지 미매칭: 일정·시간 등 조건 조정 제안
- 매칭 전: 담당자 프로필·후기 열람 가능, 채팅 불가
- 매칭 확정 화면: 「매칭 완료 / 서비스 날에 뵙겠습니다」. 채팅 버튼은 필수 CTA가 아니며 보조 진입점으로 노출
- 결제 전 제공자가 취소하면 재매칭 큐로 복귀, 고객에게는 「담당자 변경 중」으로만 안내

## 9. 결제·수수료·취소

- 결제는 건별. **서비스 종료 후** 결제 요청을 보내고, 입금 확인 후 제공자에게 정산
- 사전 20% + 잔금 80%, 방문 시작 시점 청구 방식은 사용하지 않음
- 플랫폼 수수료: 결제 총액의 15% (카드·PG 비용은 이 안에서 흡수). 상수로 분리
- 취소 수수료
  - 매칭 전, 서비스 시작 24시간 이전: 무료
  - 시작 24시간 전 이후: **20%**
  - 시작 12시간 전 이후: **30%**
  - 노쇼(당일 취소·부재): 100%
- 결제수단 1차: 카카오페이(기본), 신용카드, 계좌이체. 네이버페이는 이후
- 등록 화면은 「카카오페이로 확정하기」를 기본으로 하고 카드·계좌는 「다른 방법으로 등록」에 접어 둠
- 등록 우선순위: 보호자 사전 등록(본인 계정 연결) → 본인 간편결제 → 고객센터 링크 대리 등록
